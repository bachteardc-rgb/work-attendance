# 업무 규칙

구현 시 가장 주의해야 할 로직을 모았다. [API-SPEC.md](API-SPEC.md)와 함께 본다.

## 1. 결재 상태 전이

5종 신청 모두 동일하다.

```
                  ┌─────────────┐
   신청 등록  ───► │   PENDING   │
                  │   (대기 중)  │
                  └──────┬──────┘
                         │  관리자만 전이 가능
              ┌──────────┴──────────┐
              ▼                     ▼
       ┌─────────────┐       ┌─────────────┐
       │  APPROVED   │       │  REJECTED   │
       │   (승인됨)   │       │   (반려됨)   │
       └─────────────┘       └─────────────┘
              │
              └─► 휴가만: 부여 한도에서 차감 발생 (§3)
              └─► 교육·출장만: 결과보고 제출 가능해짐 (§4)
```

**규칙**
- `PENDING` 상태에서만 승인/반려할 수 있다. 이미 처리된 건은 재처리 불가.
- `APPROVED` / `REJECTED` 는 **종착 상태**다. 되돌리는 기능은 없다.
- 신청자 본인은 상태를 바꿀 수 없다.

> ⚠️ **프로토타입 결함**: 시간외근무·근무시간조정 결재 API에는 "이미 처리된 건" 가드가 **없다**. 휴가·교육·출장에는 있다. 통합 시 5종 모두 동일하게 가드를 넣을 것. ([INTEGRATION-NOTES.md](INTEGRATION-NOTES.md) 참고)

## 2. 시간외근무 시간 계산

서버에서 계산하며 클라이언트 값을 신뢰하지 않는다.

```
시작 "HH:MM" → startH + startM/60
종료 "HH:MM" → endH   + endM/60

totalHours = 종료 - 시작
if (totalHours < 0) totalHours += 24      // 자정을 넘긴 야간근무
totalHours = round(totalHours, 2)
```

**예시**

| 시작 | 종료 | 결과 | 비고 |
|---|---|---|---|
| 18:00 | 21:30 | 3.5 | |
| 19:00 | 21:00 | 2 | |
| 18:00 | 08:00 | 14 | 자정 넘김 |
| 09:00 | 09:00 | 0 | 동일 시각 → 0 (24 아님) |

> 휴게시간 자동 공제 없음. 24시간 초과 근무 표현 불가. 필요 시 요건 추가.

## 3. 휴가 승인 시 차감 규칙

승인(`APPROVED`) 처리는 **트랜잭션**으로 수행한다.

```
1) 신청 조회 → 없으면 오류, PENDING 아니면 오류
2) status = APPROVED 로 변경
3) 차감 대상 종류(baseType) 결정
      HALF_AM / HALF_PM  →  ANNUAL
      그 외              →  신청 type 그대로
4) year = 신청 startDate 의 연도
5) LeaveQuota(userId, year, baseType).usedDays += daysUsed
6) baseType == ANNUAL 이면
      User.annualLeaveUsed += daysUsed        // 중복 보유 필드 동기화
```

**주의사항**

- **반차는 연차에서 차감**된다. `HALF_AM`/`HALF_PM` 은 별도 부여 항목이 아니다.
- 차감 연도는 **시작일 기준**이다. 연말~연초에 걸친 휴가는 전부 시작일 연도에서 차감된다.
- ⚠️ **프로토타입 결함**: 해당 `LeaveQuota` 행이 없으면 **조용히 아무 일도 일어나지 않고** 승인만 된다. 관리자가 그 종류를 부여하지 않은 상태에서 승인하면 사용량이 집계되지 않는다. → 통합 시 **부여 없으면 승인 거부** 또는 **0으로 자동 생성 후 차감** 중 정책 결정 필요.
- ⚠️ **초과 승인 미차단**: 잔여보다 많은 일수를 승인해도 막지 않는다(잔여가 음수가 됨). 정책 결정 필요.
- 반려 시 차감은 발생하지 않는다. 승인 후 반려로 되돌리는 기능이 없으므로 **차감 복원 로직도 없다**.

## 4. 교육·출장 결과보고 규칙

```
승인(APPROVED) 상태          →  결과 제출 가능
그 외(PENDING/REJECTED)      →  결과 제출 거부
```

- 결과 제출자는 **신청자 본인만** 가능하다. 관리자도 대신 작성할 수 없다(열람만).
- 내용이 공백만이면 거부한다(`trim` 후 검사).
- **재제출(수정) 허용**. 이때 `resultSubmittedAt` 이 갱신된다. 이전 내용은 보존되지 않는다.
- 관리자 열람 목록은 `resultSubmittedAt IS NOT NULL` 인 건을 최신순 최대 50건.

## 5. 시간외근무 월 한도 규칙

### 5.1 집계 단위

```
부여:  OvertimeQuota(userId, year).monthlyHours     ← 연 1건, 매월 동일 적용
사용:  해당 "월"의 APPROVED 건 totalHours 합계
잔여:  부여 − 사용
```

**월 경계**는 UTC 기준으로 계산한다.
```
monthStart = UTC(year, month-1, 1, 00:00:00.000)
monthEnd   = UTC(year, month,   0, 23:59:59.999)   // 해당 월 말일
```

### 5.2 사용량에 포함되는 것

| 상태 | 사용량 포함 | 비고 |
|---|---|---|
| `APPROVED` | ✔ | |
| `PENDING` | ✘ | 별도 필드로 안내만 (`pendingHours`) |
| `REJECTED` | ✘ | |

### 5.3 신청 시 안내 (차단 아님)

| 조건 | 동작 |
|---|---|
| 부여 미설정(`hasQuota=false`) | "부여시간이 설정되지 않았습니다" 안내, 경고 없음 |
| 잔여 ≥ 신청시간 | 정상, 반영 후 잔여를 녹색으로 표시 |
| 0 < 잔여 < 신청시간 | 적색 표시 + 제출 시 확인창 (초과량 명시) |
| 잔여 ≤ 0 (이미 초과) | 적색 표시 + 제출 시 "이미 초과" 확인창 |

확인창에서 **취소하면 신청되지 않고, 확인하면 그대로 신청된다**(하드 차단 아님).

## 6. 달력 표시 규칙

### 6.1 조회 대상

```
반려(REJECTED) 건은 제외한다.   ← 실제로 발생하지 않은 일정이므로
대기(PENDING) 건은 포함하되 "(대기)" 표기와 반투명 처리로 구분한다.
```

### 6.2 월 겹침 판정

| 종류 | 판정 기준 |
|---|---|
| 휴가·교육·출장 (기간형) | `startDate ≤ 월말` **AND** `endDate ≥ 월초` (월과 겹치기만 하면 포함) |
| 근무시간조정 (`applyDate`) | 해당 월 내 |
| 시간외근무 (`date`) | 해당 월 내 |

기간형 일정은 **시작일~종료일 사이 모든 날짜 칸에 각각 표시**한다.

### 6.3 날짜별 "근태상황" 판정

해당 날짜의 **승인된** 일정 중 아래 우선순위로 하나를 표시한다.

```
1순위  휴가      → "휴가 (연차)"
2순위  출장      → "출장 (부산 지사)"
3순위  교육      → "교육 (○○과정)"
4순위  시간조정   → "조정 근무 09:30 - 18:30"
없으면           → "정상 근무 09:00-18:00"   (User.baseSchedule)
```

대기 중인 건은 근태상황 판정에 **반영하지 않는다**(아직 확정이 아니므로).

### 6.4 조회 범위 권한

```
일반 직원  →  본인 일정만. scope 파라미터를 무시한다.
관리자     →  scope=me(본인) 또는 scope=all(전 직원) 선택
```

> 서버에서 역할을 확인해 **일반 직원이 `scope=all` 을 보내도 `me` 로 강등**한다. 화면에서 버튼을 숨기는 것만으로 처리하지 않는다.

## 7. 일괄 부여 규칙

휴가·시간외근무 공통.

```
1) 입력값이 빈 문자열인 직원은 저장 대상에서 제외한다   ← 일부만 수정 가능
2) 숫자가 아니면 전체 거부 (400)
3) 음수면 전체 거부 (400)
4) 저장 대상이 0명이면 거부 (400)
5) 전체를 하나의 트랜잭션으로 upsert
```

- **upsert**: 기존 값이 있으면 갱신, 없으면 생성.
- 휴가에서 `leaveType == ANNUAL` 이면 `User.annualLeaveTotal` 도 함께 갱신한다.
- 부여 일수를 낮춰도 **기존 사용량(`usedDays`)은 건드리지 않는다** → 잔여가 음수가 될 수 있다(의도된 동작, 화면에 적색 표시).

## 9. 날짜·타임존 처리

프로토타입은 날짜를 **UTC 자정** 기준으로 저장한다(`new Date("2026-08-19")` → `2026-08-19T00:00:00Z`).

- 월별 조회 경계도 UTC로 계산해야 일관성이 유지된다.
- 화면 표시 시 KST(+9)로 변환해도 UTC 자정 기준이면 날짜가 바뀌지 않는다.
- ⚠️ 시각을 포함한 값(`resultSubmittedAt` 등)은 실제 시각이 저장되므로 표시 시 로케일 변환이 필요하다.

> 통합관리시스템이 KST 기준 `date` 타입을 쓴다면 그 표준을 따르는 편이 낫다. **중요한 것은 저장·조회·집계의 기준을 하나로 통일하는 것**이다.
