# 통합 시 주의사항 · 알려진 제약

> **이 문서를 가장 먼저 읽어 주세요.**
> 프로토타입은 기능 검증용으로 만들어졌습니다. 아래 항목은 **그대로 옮기면 안 되거나**, 옮기기 전에 발주처와 정책을 확정해야 하는 것들입니다.

## 1. 인증은 반드시 교체해야 한다 🔴

프로토타입의 로그인은 **테스트 편의용**이며 운영에 절대 부적합하다.

| 현재 동작 | 문제 |
|---|---|
| 이메일만 입력하면 로그인됨 (**비밀번호 검증 없음**) | 타인 계정 도용 가능 |
| 존재하지 않는 이메일이면 **계정을 자동 생성** | 임의 계정 생성 가능 |
| 이메일에 `admin` 문자열이 포함되면 **관리자 권한 자동 부여** | 권한 상승 가능 |
| 화면에 "관리자 계정으로 로그인" 원클릭 버튼 노출 | — |

**조치**: 로그인 화면(`/auth/signin`)과 인증 로직 전체를 폐기하고 **통합관리시스템의 SSO/계정 체계를 사용**한다. `Account`/`Session`/`VerificationToken` 테이블도 제거한다.

권한(`role`)은 통합관리시스템의 권한 체계에 매핑한다. 인사 담당자 = 관리자.

## 2. 결재선 정책을 먼저 확정할 것 🔴

프로토타입은 **관리자 1인 단일 결재**다. 실제 사내 규정은 보통 다르다.

확정 필요 사항:
- 부서장 1차 → 인사팀 2차 같은 **다단계 결재**가 필요한가?
- 신청자의 **부서장이 자동으로 결재자**가 되는가? (→ 조직 마스터 연동 필요)
- 대결/전결, 결재 의견, 반려 사유 입력이 필요한가?
- 승인 후 **취소·회수**가 가능해야 하는가?

이에 따라 데이터 모델(결재선·결재이력 테이블)이 추가되어야 하므로 **착수 전 확정**을 권한다.

## 3. 조직/사용자 마스터 연동 🔴

| 현재 | 통합 시 |
|---|---|
| `User` 테이블을 자체 보유 | 통합관리시스템의 **사원 마스터를 사용** |
| `department` 가 자유 문자열 | **조직 코드 FK**로 대체 |
| 직원 등록 화면(S-04-3) 자체 보유 | 인사 마스터에서 관리 → **이 화면 불필요** |

부서별 집계·조직개편 이력 관리가 필요하면 조직 마스터 연동이 필수다.

## 4. 데이터 중복 정리 필요 🟡

`User.annualLeaveTotal` / `User.annualLeaveUsed` 는 `LeaveQuota`(year=당해, leaveType=`ANNUAL`)와 **같은 정보를 중복 저장**한다.

프로토타입은 승인 시 양쪽을 함께 갱신해 동기화하지만, 중복은 언젠가 어긋난다.
→ **`LeaveQuota` 한쪽으로 일원화**할 것을 권장한다.

## 5. 프로토타입의 알려진 결함 🟡

옮기기 전에 반드시 보완해야 할 것들이다.

| # | 위치 | 내용 | 권장 조치 |
|---|---|---|---|
| D-1 | 시간외근무·근무시간조정 결재 | **이미 처리된 건을 다시 승인/반려할 수 있다**. 휴가·교육·출장에는 가드가 있으나 이 둘은 누락 | 5종 모두 `PENDING` 일 때만 전이 허용 |
| D-2 | 휴가 승인 차감 | 해당 `LeaveQuota` 행이 없으면 **조용히 차감되지 않고 승인만 된다** | 부여 없으면 승인 거부, 또는 0으로 생성 후 차감 |
| D-3 | 휴가 승인 | 잔여보다 많은 일수를 승인해도 **막지 않는다**(잔여 음수) | 초과 승인 차단 여부 정책 확정 |
| D-4 | 전 구간 | 승인 후 **반려로 되돌릴 수 없고, 차감 복원 로직도 없다** | 취소/회수 요건과 함께 설계 |
| D-5 | 신청 전반 | 등록 후 **수정·취소 기능이 없다** | 요건 확정 |
| D-6 | 휴가 신청 | `daysUsed` 를 **신청자가 직접 입력**한다. 주말·공휴일 자동 제외 없음 | 사내 달력 기준 자동 산정 검토 |
| D-7 | 근무시간조정 승인 | 승인해도 `baseSchedule` 이 **바뀌지 않는다**(이력만 남음) | "해당일만 적용" vs "이후 기본값 변경" 확정 |
| D-8 | 시간외근무 | 휴게시간 자동 공제 없음, 24시간 초과 표현 불가 | 근로기준법 요건 반영 검토 |
| D-9 | API 전반 | 미인증에 401/403 사용이 **엔드포인트마다 불일치** | 표준화 |
| D-10 | 교육·출장 결과 | 재제출 시 **이전 내용이 덮어써진다**(이력 없음) | 이력 보존 필요 시 별도 테이블 |
| D-11 | 전 구간 | **감사로그 없음** (누가 언제 승인했는지 기록 안 됨) | 결재 이력 테이블 추가 권장 |

## 6. 정책 결정이 필요한 항목 🟡

프로토타입에서 임의로 정한 것들이다. 발주처 확인이 필요하다.

| 항목 | 프로토타입 동작 | 확인 필요 |
|---|---|---|
| 시간외근무 한도 초과 신청 | **경고 후 진행 허용** (차단 안 함) | 하드 차단할 것인가? |
| 시간외근무 사용량 집계 | **승인 건만** 집계, 대기분은 안내만 | 대기분도 선차감할 것인가? |
| 시간외근무 한도 단위 | 연도별 1건 등록 → **매월 동일 적용** | 월별로 다른 한도가 필요한가? |
| 미사용 시간 이월 | **없음** (월 단위 리셋) | 이월 필요한가? |
| 휴가 차감 연도 | **시작일 기준** | 연말~연초 걸친 휴가 처리 방식 |
| 달력 반려 건 | **표시 안 함** | 맞는가? |
| 결과보고 제출 기한 | **없음** (언제든 제출·수정) | 기한 제한 필요한가? |
| 반차 | **연차에서 차감** | 맞는가? |

## 8. 데이터 이관

프로토타입에 쌓인 데이터는 **검증용 테스트 데이터**이며 이관 대상이 아니다.

실제 이관이 필요한 것은 통합 시점의 **직원별 잔여 연차**이며, 기존 인사 시스템/엑셀에서 `LeaveQuota` 에 해당하는 값(연도·종류별 부여일수·사용일수)으로 초기 적재해야 한다. 일괄 부여 화면(S-04-4)으로도 초기 세팅이 가능하다.

## 9. 비기능 요구 (구현 시 유의)

| 항목 | 내용 |
|---|---|
| 권한 재검증 | 화면 숨김만으로 처리하지 말 것. **모든 관리자 API에서 서버가 역할을 재확인**해야 한다 |
| 조회 범위 강등 | 일반 직원이 전체조회 파라미터를 보내도 서버가 본인 범위로 강등해야 한다 |
| 트랜잭션 | 일괄 부여·휴가 승인 차감은 **원자적**으로 처리 |
| 타임존 | 저장·조회·집계 기준을 **하나로 통일**. 월 경계 계산 시 오차 주의 |
| 응답 경합 | 달력 월 이동처럼 빠르게 파라미터가 바뀌는 화면은 **늦게 도착한 이전 응답이 화면을 덮지 않도록** 처리 |
